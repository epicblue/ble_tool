> 结论性数字都可以用 `python3 tools/algo_sim/experiments.py` 复现。

- 基线版本：v1.1.2（10 个动作，`d038fd0` → `5eb39ba`）
- 配套工具：`tools/algo_sim/`（判定器的 Python 逐行复刻 + 回归 + 敏感性实验）

## 1. 结论摘要（如果只看 5 行）

> 状态（2026-10-27）：①②④⑤ 已修并在 Python 复刻 + Java 中落地；②（横滚补偿）与 ⑥ 以后待做。
> 下面的数字是**修复前**的现场，用于说明问题的严重程度；修复后的实测见第 4 节各项末尾的"实测"与第 5 节进度表。

1. **计时类成绩会被"宽限期"虚增**：站起来休息 600ms 也会被算进靠墙蹲成绩（实测 3432ms → 3894ms）。这是正确性问题，最该先修。
2. **关节角在"镜头不正对动作平面"时被透视缩短**：镜头偏 41° 时，92° 的肘角会被量成 108°，俯卧撑从 3 次全对变成 3 次全判"幅度不足"。
3. **机位横滚没有补偿**：手机歪 30° 时，平板支撑、倒立、靠墙蹲的成绩直接归零，深蹲的"前倾 55°"阈值也会被横滚吃掉一半预算。
4. **双侧关节角直接取平均**：一侧关键点被污染（置信度 0.6、角度偏 48°）会把平均值拖偏 24°，足够把"撑到位"误判成"没撑起"。
5. **走路与跑步无法区分**：90/120/160 步/分全都按"跑步计步"计，动作名与能力不匹配。

## 2. 现状：每个动作靠什么判定

| 动作 | 主判据 | 兜底/辅助 | 抗噪 | 最易失效的场景 |
| --- | --- | --- | --- | --- |
| 俯卧撑（含折凳、不标准） | 肩-肘-腕角 `TOP 152° / DEPTH 100°` | 手腕下降比例 `FULL_DEPTH 0.85`（正对镜头） | 平滑 0.5、`MIN_REP_MS 350`、丢帧 500ms | 镜头斜对（角度缩短）、单侧手臂被遮挡 |
| 深蹲 | 膝角 `STEP 155°/START 140°/DEPTH 100°`，**或**髋下降 `≥0.35×躯干`（到位） | 髋下降 `0.18×躯干` 或膝角 `≤125°` 算"明显下蹲" | 平滑 0.5、`MIN_REP_MS 320` | 横滚 |
| 引体向上 | 肘角 `HANG 150°/PULL 95°` + 身体上升 `0.10×躯干` | 手腕高于肩 `0.15×躯干` | `MIN_REP_MS 400`、丢帧 600ms | 没有横杆参照、下巴是否过杆无法判断 |
| 平板支撑 | 躯干水平 `<30°`、`sagRatio ≤0.15`、手腕下垂 `>0.05` | 髋部抬起 `>0.02`、`HoldClock` 只计时有效时间 | `ARM 500`、`GRACE 800`、丢帧 600 | 横滚 |
| 倒立 / 靠墙倒立 | 倾斜 `25°/32°`、髋横移 `0.18/0.30×躯干` | 靠墙时脚踝漂移 `0.25` | `ARM 300`、`GRACE 700`、12 帧历史 | 横滚、机位过低 |
| 靠墙蹲 | 膝角 `60~110°`、髋膝高差 `≤0.30×躯干`、躯干 `≤30°` | 稳定度 = 膝角标准差、`HoldClock` 只计时有效时间 | `ARM 400`、`GRACE 800` | 横滚 |
| 跑步计步 | 左右脚踝高度差 `>0.16×躯干` 的符号翻转 | 步频 `180~1600ms`、连续 2 帧、步频+躯干起伏分走/跑 | 丢帧 700ms | 脚踝出画 |

滤波与度量（所有动作共用）：

| 组件 | 参数 | 作用 |
| --- | --- | --- |
| `PoseSmoother` | `MIN_CONF 0.3`、`BASE_ALPHA 0.45`、`MAX_JUMP_RATIO 0.6`、`HOLD_MS 350` | 指数平滑 + 跳变剔除 + 短暂丢失保持 |
| `BodyMetrics` | `CONF 0.5`、`MIN_SCALE 0.04`、`FRONTAL_RATIO 0.62` | 尺度无关比例量、视角判定 |
| `PoseMath` | 关节角按左右两侧**置信度感知**融合（`CONF_GAP 0.25`、`DISAGREE_ANGLE 35°`） | 单侧缺失或置信度低时自动取可信的那一侧 |

## 3. 问题清单（按严重程度）

### P0-1 计时类把中断时间算进成绩 ✅ 已修复

`PlankTimer` / `WallSitTimer` / `HandstandTimer` 都用 `duration = lastGoodMs - holdStartMs`。
宽限期（700~800ms）内姿势不合格时计时不结束，等回到合格姿势后，**中间那段休息也被算作保持**。

实测（`experiments.py` 实验 G，靠墙蹲 GRACE=800ms）：

| 真实中断 | 结果 |
| --- | --- |
| 0ms（连续保持） | 3432ms |
| 300ms | 3564ms（+132ms） |
| 600ms | 3894ms（+462ms） |
| 900ms | 切成两组，1914ms |

影响：计时类成绩系统性偏高，最长可达 +800ms/组；平板支撑、倒立同理。
**修法**：改成"只在合格帧之间累加 `now - lastGoodMs`"，即只在两帧都合格时把时间计入。
`getCurrentHoldMs()` 同理，界面上的秒表在宽限期内应停住而不是跳一下。

### P0-2 关节角的透视缩短（镜头斜对动作平面） ✅ 已修复

关节角在**动作平面正对镜头**时才准确。横向压缩（模拟镜头偏转）后：

| 横向压缩 kx | ≈镜头偏角 | 肘角真值 92° 读成 | 膝角真值 88° 读成 | 俯卧撑 3 次 | 深蹲 3 次 |
| --- | --- | --- | --- | --- | --- |
| 1.00 | 0° | 92.0° | 88.0° | 3 好 | 3 好 |
| 0.75 | 41° | 108.2° | 104.3° | 0 好 / 3 差 | 0 好 / 3 差 |
| 0.50 | 60° | 128.5° | 125.3° | 0 好 / 0 差 | 0 好 / 3 差 |

而**沿重力方向的位移完全不受影响**：深蹲髋部下移在 kx=1/0.75/0.5 下都是 `1.25×躯干`。

> 已有"手腕下降比例"兜底，但只在 `view == FRONTAL`（肩宽/躯干 ≥0.62）时优先使用；
> 41° 这种斜对场景被判成 `SIDE`，兜底不生效。

### P0-3 机位横滚没有补偿

所有"竖直/水平"类的判据都假设图像 y 轴就是重力方向（`torsoAngleFromVertical`、`wristDropRatio`、脚踝高度差）。把画面整体旋转（手机歪放/三脚架没调平）：

| roll | 俯卧撑 | 深蹲 | 平板 | 倒立 | 靠墙蹲 | 跑步 |
| --- | --- | --- | --- | --- | --- | --- |
| 0~20° | 3 好 | 3 好 | 3432ms | 3432ms | 3432ms | 7 步 |
| 30° | 3 好 | 3 好 | **0** | **0** | **0** | 7 步 |

原因：横滚直接加在"躯干与竖直方向夹角"上——站立时 roll=10° 就被算成前倾 10°。
平板（30°）、靠墙蹲（30°）、倒立（25°）的阈值预算几乎被横滚吃光；深蹲的 55° 也只剩一半。

### P1-4 双侧关节角直接平均，单侧污染会拖偏 ✅ 已修复

`PoseMath.averageAngle()` 在两侧都可信时取算术平均。实测（撑起位，左臂关键点被污染但置信度仍有 0.6）：

| 融合方式 | 读数 | 偏差 |
| --- | --- | --- |
| 直接平均 | 131.0° | **−24.0°** |
| 置信度加权 | 135.8° | −19.2° |
| 只取更可信的一侧 | 155.0° | 0° |

131° 已低于 `TOP_ANGLE - 6 = 146°`，会破坏"撑起位基准校准"，并让状态机在错误的位置切换。

### P1-5 走路与跑步无法区分 ✅ 已修复

`RunStepCounter` 只看脚踝高度差符号，90/120/160 步/分一律计步。动作名是"跑步计步"，但用户走路、原地踏步也会被计入（这对"计步"无可厚非，对"跑步"则是错误结论）。

### P1-6 阈值是绝对值，缺个体化校准

每个人肘/膝角度极限不同（柔韧性、体型、折凳高度）。现在 `DEPTH 100°`、`STAND 155°` 是全体用户共用；偏胖、柔韧性差的用户会被系统性地判"幅度不足"。目前只有俯卧撑做过一次 `topDrop` 自校准。

### P2-7 快动作被静默丢弃

`MIN_REP_MS 350/320/400` 会把整次 <0.4s 的动作直接忽略，**连"不标准"都不记**。实测 15fps + 每半程 3 帧（整次 0.4s）→ 0 好 0 差。对爆发式俯卧撑/快速深蹲属于漏计。

### P2-8 丢帧只"保持位置"，不外推

`PoseSmoother` 在 ≤350ms 丢失时保持最后位置。快速动作中途丢帧 → 关键点停在半程，等恢复时容易被判成"回到起点"，导致漏计一次。

### P2-9 引体向上缺"下巴过杆"和 kipping 判定

现在只有"身体上升 ≥0.10×躯干"和肘角，无法判断下巴是否过杆；摆浪（kipping）也会被算作有效次数。

### P2-10 质量评分二值化

`badReps` 只有"标准/不标准"两种；没有深度百分比、节奏（离心/向心时长）、左右对称这类连续指标，历史趋势里也就只能看次数。

### P2-11 干扰目标

ML Kit 只返回一个最高分的人体，但宠物、路人、镜面反射会让关键点在两人之间跳变。当前靠 `MAX_JUMP_RATIO` 剔除单帧，长时间跳变仍会污染。

### P2-12 缺真实数据与基线

现有测试全是合成关键点。**没有任何真机录制的标注数据**，因此每次调阈值都是"改完看感觉"。这是所有改进的前置条件。

## 4. 改进方案

### 阶段一（P0，先修正确性与最大误差来源）

#### ① 计时器只累计"有效时间" ✅ 已完成

- 新增 `analysis/HoldClock.java`：维护 `validMs`、`lastGoodMs`、`graceMs`、中断原因；
  只在连续两个合格帧之间累加 `now - lastGoodMs`。
- `PlankTimer` / `WallSitTimer` / `HandstandTimer` 改为委托给它；`getCurrentHoldMs()` 在宽限期内停住。
- 顺带产出"有效保持率 = validMs / (validMs + 中断时长)"，可直接存进 `Session`。
- 涉及：3 个判定器 + `HoldAnalyzer` 默认方法（新增 `getInterruptMs()`）。
- 验收：中断 0/300/600ms 分别得到同一时长（不再随中断增长）。
- 工作量：约 0.5 天（含回归用例）。
- **实测**：连续 50 帧保持 = 3234ms；中间插入 198 / 594 / 792ms 中断后仍为 3168ms
  （修复前分别是 3432 / 3564 / 3894ms）。差值 66ms 是"中断那一帧本身"的采样间隔。
  实现见 `analysis/HoldClock.java`，`getInterruptMs()` 可直接算有效保持率。

#### ② 重力对齐（横滚补偿）

- 相机侧用 `SensorManager.getRotationMatrixFromVector()` 取设备相对重力的 roll（`CameraController` 回调里已有帧时间戳，接传感器成本低）。
- `pose/GravityAlign.java`：把关键点绕画面中心反向旋转 `-roll`，得到"重力对齐坐标系"，之后所有 y 方向判据都在该坐标下进行。
- `PoseLog` 增加每帧 roll（**版本号 1 → 2**，读取端按版本兼容旧文件），保证**回放与实时判定完全一致**。
- 无传感器权限/不可用时退化为 roll=0，并在界面提示"请把手机放平"。
- 验收：roll ∈ [−30°, 30°] 时各动作结果与 roll=0 一致（当前 30° 时平板/倒立/靠墙蹲归零）。
- 工作量：约 1.5 天（含日志格式兼容与单测）。

#### ③ 透视鲁棒：位移为主 + 透视因子检测 ✅ 已完成（判据已调整）

- `pose/ProjectionQuality.java`：
  - `armForeshorten = |肩-腕| / 躯干长度`，正常侧对约 1.0；<0.75 视为"手臂被压扁"。
  - `legForeshorten = |髋-踝| / 躯干长度`（正常约 1.8~2.2），<1.4 视为"腿被压扁"。
  - 直接用该因子替代现在的 `view == FRONTAL` 作为"是否改用比例判据"的开关（更贴近物理原因）。
- `PushUpCounter`：`depth = max(angleDepth, dropDepth)`，但当 `armForeshorten < 0.75` 时**只用 dropDepth**（角度不可信）；
  `topDrop` 校准也允许在角度不可信时进行（用"最近 3 帧的最低手腕位置"）。
- `SquatCounter`：新增 `hipTravelDepth`——以站立时为 0、`0.45×躯干` 为 1.0，`depth = max(angleDepth, hipTravelDepth)`；
  `MIN_HIP_TRAVEL` 从"必须满足"改为"参与评分"。
- 验收：kx=0.75（≈41° 斜对）时俯卧撑/深蹲均为 3 好 0 差；kx=1 时不回归。
- 工作量：约 1.5 天。
- **实测与调整**：原计划的 `armForeshorten` 判据方向是错的 ——
  镜头偏转时"肩-腕距离"在图像上**反而变大**（kx=1.0 / 0.75 / 0.5 → 1.00 / 1.33 / 2.00），
  不能用来判断"手臂被压扁"。改为不设开关、直接 **`depth = max(angleDepth, dropDepth)`**：
  两路都是"下限估计"，取大者既不漏判也不会因单路失效而归零。实测
  - 俯卧撑 kx=1.0 / 0.75：3 好 0 差（改前 kx=0.75 为 0 好 3 差）；
  - 深蹲 kx=1.0 / 0.75 / 0.5：3 好 0 差（改前 kx=0.75 为 0 好 3 差）；kx=0.35 时信号完全消失，0 好 0 差（可接受）。

### 阶段二（P1，体验与一致性）

#### ④ 单侧可信度融合 ✅ 已完成

- `PoseMath.averageAngle()` 改为 `weightedAngle()`：
  - 置信度差 >0.25 时只取高的一侧；
  - 角度差 >35° 时视为一侧异常，取高置信度侧，并把该帧标为 `degraded`；
  - 其余情况按置信度加权。
- 验收：实验 E 的污染场景下读数偏差 ≤5°（当前 24°）。
- 工作量：0.5 天。
- **实测**：置信度差 0.3（左 0.6 / 右 0.9）时直接取右侧，读数 155.0°（偏差 0°，直接平均是 131°）。
  实现保留 `averageAngle()` 原签名（置信度感知版），`CONFIDENCE_GAP = 0.25`、`DISAGREE_ANGLE = 35°`。
  注意：**只做加权平均是不够的**（加权后 135.8°，仍偏 19°），必须用"硬剔除 + 取高置信侧"。

#### ⑤ 走/跑分类（或改名） ✅ 已完成

- 用两项指标：步频（>140 步/分为跑）与躯干上下振幅（髋部 y 的峰峰值 / 躯干长度，跑步 >0.06）。
- 输出 `RunStepCounter.getGait()`（`WALK` / `RUN` / `UNKNOWN`），界面显示"跑步 160 步/分"或"走 96 步/分"，成绩仍记步数。
- 备选（更省事）：把动作改名为"计步 / 原地跑计步"，并在文档里写清包含走路。
- 验收：实验 F 三档步频能正确分类。
- 工作量：1 天。
- **实测**：阈值定为 `RUN_CADENCE = 150`、`WALK_CADENCE = 120`、`HIP_BOB_RUN = 0.05`；
  慢走 90 / 快走 120 → `WALK`，慢跑 160 → `RUN`，135 步/分 + 躯干起伏 → `RUN`、无起伏 → `WALK`，
  站立不动 → `UNKNOWN`。界面显示"跑步 160 步/分"。

#### ⑥ ROM 自校准（个体化）

- 新增 `analysis/RomCalibrator`：每组动作前 2 次有效往返学习"上端/下端"，把绝对角度阈值换算成"本次 ROM 的 20%~85%"。
- 写入 `UserProfile`（每人一份，可手动重置）。
- 验收：模拟"柔韧性差"（最低点 115°）用户在自校准后仍判为有效（当前判"幅度不足"）。
- 工作量：1.5 天。

### 阶段三（P2，进阶）

| 项 | 做法 | 验收 |
| --- | --- | --- |
| ⑦ 快动作不静默丢弃 | `MIN_REP_MS` 改为按 fps 缩放（`max(220ms, 3.5 帧)`），过短的动作记 `tooFast` 而不是丢弃 | 15fps、0.4s 动作至少能进"不标准" |
| ⑧ 丢帧外推 | 丢失 <350ms 时用最近两帧线性外推（置信度递减），并在 `PoseLog` 里标记 `interpolated` | 中速动作中丢 2 帧不漏计 |
| ⑨ 引体进阶 | 用 `鼻/下巴 y` 与手腕 y 比较判断"过杆"；用髋部 x 摆动幅度（>0.12×躯干）判 kipping | 摆浪被判不标准 |
| ⑩ 连续质量分 | `RepEvent` 增加 `depthPercent / tempoMs / symmetry`；`Session` 存平均质量分 | 历史里能看到"质量 78%" |
| ⑪ 干扰目标 | `CameraController` 里用人体框面积 + 关键点平均置信度做多帧一致性投票，跳变时暂停判定 | 有人路过不再误计 |
| ⑫ 真机数据与基线 | 录制 20~30 段带标注的 `.dat`（覆盖 3 种机位 × 5 个动作），作为 `app/src/test/resources/pose-golden/`，JUnit 里跑 `ReplayTimeline` 对比标注 | 每次提交自动算准确率，改动可量化 |

## 6. 评估指标（统一口径）

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 计数误差 | \|识别次数 − 真实次数\| | ≤1（10 次以内），≤5%（20 次以上） |
| 误计率 | 非目标动作场景下误计的条数 / 总片段 | 0（站立、走动、递物、坐下） |
| 计时误差 | \|识别时长 − 真实时长\| | ≤0.3s，且不含中断时间 |
| 视角鲁棒性 | 侧对 / 45° / 正对 三种机位的准确率之差 | ≤10 个百分点 |
| 横滚鲁棒性 | roll −30°~30° 与 0° 的结果一致性 | 完全一致 |
| 判定确定性 | 同一段骨架重复判定结果 | 100% 一致（现在是确定的，回放要保住） |

## 7. 风险

- **日志格式变更**（②）会让旧版本读不了新文件/反之：必须同时写版本兼容分支，并在 `PoseLog` 单测里覆盖 v1/v2。
- **传感器接入**增加 `CameraController` 复杂度，部分设备 `ROTATION_VECTOR` 不可用 → 必须有无传感器降级路径。
- **自校准**可能把错误动作也"学"进 ROM（比如第一次就做了半个），需要"只采用最极端值 + 可手动重置"。
- 阈值分散在各判定器里，改一处容易漏 —— 建议在阶段二顺手抽出 `PoseTuning.java`（ROADMAP 2.1 已有该计划）。

## 8. 附：复现方式

```bash
pip install javalang          # 仅 java_static_check.py 需要
python3 tools/algo_sim/regression.py     # 40 条行为断言（应全部 PASS）
python3 tools/algo_sim/experiments.py    # 本文所有数字的来源
python3 tools/java_static_check.py       # 符号级自查（无 SDK 时用）
```

`tools/algo_sim/replica.py` 是 Java 判定器的逐行复刻；改 Java 阈值时请同步改它，
否则复刻失去意义（回归脚本会在数字对不上时暴露出来）。
